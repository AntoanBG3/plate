# The c5 search and parse slowdown, explained

The 2026-11-05 audit measured food search at 89.6 ms alone and 912.7 ms with five simultaneous requests, and a parse with the fallback parser at 550.1 ms alone and 6,105.3 ms at five. Throughput fell from 11.4 to 5.3 searches a second as concurrency rose. It left the cause open and refused to use c5 numbers as budgets until it was found.

## Measurements, 2026-11-23

Same machine and setup as the audit: Mac16,13, Docker Desktop VM with 10 CPUs, `tools/perf/setup.sh 730` (two years of synthetic data for five accounts, app at 1 CPU and 256 MiB, Postgres 18 at 256 MiB). Median of five batches, after two warm-up batches; "chicken breast" for search, three foods for the parse. `tools/perf/concurrency.mjs` reproduces these.

| Revision | Database | Search c1 → c5 (ms) | Parse c1 → c5 (ms) |
|---|---|---|---|
| main 6b80fdc | no CPU cap, not yet analyzed | 105 → 149 | 377 → 419 |
| audit baseline 462ef11 | no CPU cap, not yet analyzed | 104 → 138 | 537 → 692 |
| main 6b80fdc | analyzed, capped at 1 CPU | 27 → 200 | |
| main 6b80fdc | analyzed, capped at 0.5 CPU | 27 → 495 | |
| main 6b80fdc | analyzed, no cap | 27 → 43 | 58 → 112 |

During the uncapped concurrent runs, every sampled Postgres session was on CPU, with no lock or I/O waits.

## What it was

The code was not the cause. The audit's own revision doesn't slow down tenfold either, so neither the app nor anything changed since does it. A CPU cap on the database reproduces the pattern: fast alone, then five searches queue behind one CPU's worth of time. The audit records that some setup runs had "an initially incorrect DB CPU cap" and were discarded. The c5 and ramp figures behave as if they came from such a database, or from a host busy with other work during those runs. The original runs can't be replayed, so that part is inference. The reproduction above is not.

Production's database has no CPU cap (`nanocpus=0` in the audit's production snapshot) on wizard's four cores, so it isn't affected.

A second, separate effect: the perf database was seeded and measured before Postgres had analyzed the foods table. Without statistics, the planner scanned all 11,838 foods for every search (about 100 ms); after `ANALYZE`, the same search used the trigram index (22 ms). Production has statistics for the table. This explains why the audit's c1 search (89.6 ms, a sequential scan in its EXPLAIN) was slower than production plans for most searches.

## Changes

- `tools/perf/setup.sh` runs `ANALYZE` after seeding and refuses to serve if the database container has a CPU cap.
- `tools/perf/concurrency.mjs` measures c1 against c5 and prints the database's CPU cap and when the foods table was analyzed before any numbers.
- No app change: with an uncapped, analyzed database, five simultaneous searches take 1.6 times as long as one (27 → 43 ms) and parses 1.9 times (58 → 112 ms), which is ordinary sharing.
