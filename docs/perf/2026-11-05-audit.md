# Repa performance and reliability audit — 2026-11-05

Status: measurement in progress. Baseline source commit `462ef118827b00839941eab87cceb2a106c93065`; branch `perf-audit`, cut from current local main (28 commits ahead of origin). No application fixes, pushes, merges or deployments are part of this audit.

## Hypotheses recorded before measurement

1. Phone round trips and transition time still dominate warm tab navigation; Razor itself may remain cheap.
2. Active workout restore has per-exercise history queries; increasing history and exercises may increase server work disproportionately.
3. Food parse waits for parser, matching and optional naming sequentially; production recorded stage latencies are needed to rank changes without spending API credits.
4. Two years of food and bodyweight history may increase Today/Progress and repeat-food costs despite stable query counts.
5. Whole-cache service worker installation and replacement may impose unnecessary cold/update bytes on gym mobile data.
6. A fetch that never resolves may block the single-flight set replay loop on bad signal.
7. Database/memory limits, startup work, deploy interruption, restore validation and SSD exposure may be more consequential than throughput.
