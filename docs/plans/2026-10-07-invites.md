# Phase 12: Invites — implementation plan

## Context

Antoan wants to let a few people he knows into Plate. Sending mail from wizard would work badly: residential IPs land in spam. The design avoids email entirely. A `Dev` account makes a single-use invite link and sends it over Viber or Messenger, and the link itself proves the invite was meant. SPEC.md now describes this (sections 1, 4, 9, 12 and Phase 12, edited this session but not yet committed). Phase 12 also adds `reset-password` and `delete-user` to the CLI, because email-based recovery is gone and invited people should be able to leave.

The work happens on a new branch `invites`. Step 0 commits the SPEC change and this plan. Each later step is its own commit. Test cadence follows memory: after each step, run the affected tests plus all Core and Web tests. Run the full browser suite at the end and before merging.

## Step 1: Core rules (TDD)

New `src/Plate.Core/Domain/Invite.cs` with the entity from SPEC 4: `Id`, `TokenHash` (byte[32]), `Note`, `CreatedByUserId`, `CreatedAt`, `ExpiresAt`, `RedeemedAt`, `RedeemedByUserId`, `RevokedAt`. Alongside it, a static `InviteRules` class:
- `MaxOpen = 5`, `MinDays = 1`, `MaxDays = 30`, `DefaultDays = 7`, `MaxNoteLength = 100`.
- `Status(Invite, now)` returns `Redeemed`, `Revoked`, `Expired` or `Open`, checked in that order. `ExpiresAt <= now` counts as expired, which matches the SQL condition `ExpiresAt > now`.
- `NewToken()` returns `(string Token, byte[] Hash)`: 32 bytes from `RandomNumberGenerator`, encoded with `System.Buffers.Text.Base64Url` (43 chars).
- `Hash(string token)` is SHA-256 of the UTF-8 bytes. A token that is malformed or the wrong length still hashes; it just matches nothing.

Tests go in `tests/Plate.Core.Tests/InviteRulesTests.cs`:
- status precedence (redeemed beats revoked beats expired)
- the expiry boundary at exactly `now`
- the token is 43 URL-safe characters
- two tokens differ
- the hash is deterministic and 32 bytes

## Step 3: InviteService and redemption

> As built: create, list and revoke live in `Features/Admin/InviteAdmin.cs` (English, excluded from the Bulgarian catalogue like the other admin code); `Features/Users/InviteService.cs` keeps only `IsOpenAsync` and `RedeemAsync`. The open-invite query is `InviteRules.WhereOpen` in Core. `CreatedByUserId` is null for CLI-made invites.

`UserCreator` (`src/Plate.Web/Features/Users/UserCreator.cs`) gets an optional `Language language = Language.English`, which is written to the profile. CLI callers are unchanged.

New `src/Plate.Web/Features/Users/InviteService.cs`, scoped and registered in Program.cs, which uses `AdminAuditLog`, `IFeedbackNotifier`, `TimeProvider` and `UserCreator`:
- `CreateAsync(createdBy, note, days)`:
  - refuses when 5 invites are open
  - validates days and note
  - stores the hash
  - returns the raw token once
  - audits `invite-create` with the target being the id and the note
- `ListAsync(bool all)`: open invites by default; all of them, newest first, when `all` is set.
- `RevokeAsync(id)`: only an open invite can be revoked. Audits `invite-revoke`.
- `IsOpenAsync(token)`: used by the join GET.
- `RedeemAsync(token, name, email, password, language)`:
  - Opens `db.Database.BeginTransactionAsync`. There is no retrying execution strategy configured, so a manual transaction is safe.
  - Runs `ExecuteUpdateAsync` on `TokenHash == hash && RedeemedAt == null && RevokedAt == null && ExpiresAt > now`, setting `RedeemedAt`. Zero rows means `Invalid`. Under READ COMMITTED, a second concurrent redeemer blocks on the row lock and then sees zero rows.
  - Calls `UserCreator.CreateAsync` on the same scoped context, so Identity's save joins the transaction. On errors it rolls back and returns them, which leaves the invite open.
  - Sets `RedeemedByUserId`, commits, audits `invite-redeem` (target is the email, detail is the note), and sends `EnqueueText("Invite redeemed: <note> → <name>")`.
- Add the `AuditActions` constants `InviteCreate`, `InviteRevoke`, `InviteRedeem`, `PasswordReset` and `UserDelete` in `Features/Admin/AdminAuditLog.cs`.

Tests go in `tests/Plate.Web.Tests/InviteTests.cs` and use `PostgresFixture` and `AppFactory`:
- a sixth open invite is refused
- revoke works
- the happy path creates the account and profile with the chosen language
- used, revoked, expired and unknown tokens each create nothing
- two redemptions of one token via `Task.WhenAll` on two scopes produce one account
- a taken email and an 11-character password each leave the invite open
- an audit row is written
- a Telegram text is sent; reuse the `Telegram` handler pattern from `AdminTests.cs:337`

## Step 4: Join page

- In Program.cs, add a `RateLimits.Join` policy using `PerIp(http, config.GetValue("RateLimits:JoinPerWindow", 10), 15 min)`, and add the constant next to the others.
- New `src/Plate.Web/Controllers/JoinController.cs` at `[Route("join")]`, with `[AllowAnonymous]` and `[EnableRateLimiting(RateLimits.Join)]` at class level so GET and POST share one budget. Every response sets `X-Robots-Tag: noindex`.
  - Language is resolved in this order: `?lang=en|bg`, then the `gym.lang` cookie, then `Accept-Language` starting with `bg`. The action sets `CultureInfo.CurrentUICulture = Localizer.Bulgarian` when it resolves to Bulgarian. This mirrors `UserPreferencesMiddleware`, which only knows cookies for anonymous visitors.
  - GET `{token}`:
    - signed in: show the "log out first" message
    - not open: show the single invalid message
    - otherwise: show the form
  - POST `{token}`: calls `RedeemAsync`. On success it calls `SignInManager.SignInAsync(user, isPersistent: true)`, runs `UserPreferencesMiddleware.Remember` for the language cookie, and redirects to `/`. `OnboardingRedirectMiddleware` then sends the new account to `/welcome`. On errors it re-renders with the email and name kept. A signed-in POST is refused the same way as the GET.
- New `Views/Join/Index.cshtml` modelled on `Views/Account/Login.cshtml` (`.auth`, `HideTabs`): name, email, password with `autocomplete="new-password"`, and an English/Български switch made of two links that reload with `?lang=`. The choice is posted as a hidden field. There are no inline scripts.
- Add the Bulgarian strings to `Resources/strings.bg.json`, using informal "ти" and dots in numbers, and regenerate `strings.keys.json` with `GYM_WRITE_KEYS=1`.
- Tokens must stay out of the error log. `ErrorCaptureHandler` records the raw `Request.Path` (`Features/Feedback/ErrorRecorder.cs:112`), so it needs to use the endpoint's route pattern when one exists, or at least rewrite `/join/<anything>` to `/join/{token}`.

Tests go in `JoinTests.cs`:
- valid GET shows the form
- invalid GET shows the message and no form
- `Accept-Language: bg` renders Bulgarian
- the POST signs in and the next GET of `/` redirects to `/welcome`
- a signed-in visitor doesn't consume the token
- the eleventh request returns 429; use `settings` on `AppFactory`
- the `noindex` header is present
- an exception on `/join/<token>` stores no token in `ErrorEvents`

## Step 5: CLI

The work is in `src/Plate.Web/Cli/` and Program.cs; add each command name to the stderr-logging condition and to the dispatch. Each command takes `TextWriter? output` and `TextReader? input`, following `AiCommand`, so the tests can drive them.
- **`InviteCommand`** (`invite create [--note ...] [--expires 7d]`, `list [--all]`, `revoke <id>`). The link base is `https://{Passkeys:ServerDomain}`, falling back to `https://plate.peychev.uk`. That setting is already set on wizard, so `.env.example` needs no new variable.
- **`ResetPasswordCommand`** (`reset-password --email`):
  - Reads the password like `CreateUserCommand.ReadPassword`; refactor that to take a `TextReader` when input is redirected.
  - Calls `GeneratePasswordResetTokenAsync` and then `ResetPasswordAsync`, which validates the length and updates the security stamp.
  - Then calls `SetLockoutEndDateAsync(null)` and `ResetAccessFailedCountAsync`.
  - Audits `password-reset`.
- **`DeleteUserCommand`** (`delete-user --email [--yes]`) is backed by a new `Features/Users/UserDeleter.cs`. All of this runs in one transaction:
  - Refuse if the account is the last `Dev`.
  - Delete Sets, SessionExercises and Sessions, then TemplateExercises and Templates, explicitly with `IgnoreQueryFilters().ExecuteDeleteAsync`. Their FKs to `Exercise` are `Restrict` (`AppDbContext.cs:86,108`), so cascading from the user row can fail when a session uses one of the user's own custom exercises.
  - Null `ErrorEvents.UserId` for the account.
  - Call `UserManager.DeleteAsync`, which cascades the rest; `Invite.RedeemedByUserId` is set to null by its FK.
  - Audit `user-delete` with the email in the detail.
  - Confirmation: re-type the email unless `--yes` is given.

Tests:
- `invite create/list/revoke` output, with the token printed once and absent from `list`
- `reset-password` changes the hash and stamp (an old cookie client gets signed out after stamp validation; assert the stamp changed) and the new password logs in
- delete-user: build an account with every kind of user-owned row, including a custom exercise used in a session and a template, feedback with an attachment, a parse run and an onboarding chat; reuse the setup from `UserIsolationTests`
- after deleting, assert zero rows for that user in every user-owned `DbSet` with `IgnoreQueryFilters`, and that the other account is untouched
- the last Dev is refused
- a wrong confirmation aborts

Also add a third account to `UserIsolationTests`, or a separate test that creates it through an invite and checks it can't read A's or B's rows.
