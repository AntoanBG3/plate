## 2. Restore check (`changes/restore-check`)

Extend `tools/restore-drill.sh` with an app stage, then run it on wizard:
- Dump and keys both come from the nightly snapshot (`/mnt/storage/backups/latest`), read through a container as the script already does; the live `keys/` would prove nothing about the backup.
- Compare tables, columns and counts before the app starts, since startup migrates the copy.
- Start the existing `plate-app` image (no rebuild on the SSD) against the restored database on an internal-only Docker network under its own container name, never on `tunnel`, with no Telegram or OpenRouter variables and nothing read from `.env`.
- Inside the drill, create a throwaway user with the CLI, sign in over HTTP from a container on the same network, and check that the key ring decrypts (an antiforgery round trip) and no new key file was written.
- The trap removes every container, network and temporary file.
- Also report the nightly snapshot's date and size, and the predeploy dumps present. SMART health and the PC copy need sudo or the PC, so they are written up as commands for Antoan.
- README's restore section describes the new stage. No SSD replacement.

## 3. Per-100 ml labels (`changes/label-ml-basis`)

- `FoodItem.Unit` (`Grams` or `Millilitres`, default `Grams` for every existing row). A label read with `per_100ml` fills the manual form with an ml unit; the form's amount fields show ml; Save keeps the unit.
- `FoodLogEntry` and `SavedMealItem` snapshot the unit, so a past day keeps what it showed. Existing rows default to grams.
- Every place an amount is shown or entered uses the unit: entry page, Food day, Recent, search, barcode result, Check foods, saved meals, the grams sheet, last amount and usual amount, export. The 1 to 3,000 limit applies to ml the same way.
- Text parsing: the parser's grams go into an ml food unchanged (a typed "250 ml" and "250 g" are both 250 units); the matcher's count × serving uses the food's serving in its own unit.
- Persisted JSON that carries amounts gets the unit under a fixed property name, with a pinned sample test.
- SPEC 6.6 rule 4 and section 4 change; README where it describes the label reader.
- Recipe rule (for section 9 below): an ml ingredient counts 1 ml as 1 g toward the raw weight, and a recipe is always per 100 g. Written into SPEC 5.12 on the recipes branch; when both are merged, the editor's rows should show ml for such an ingredient.

## 4. Activity and AI cost in the digest (`changes/digest-activity-cost`)

- Retention 180 days in the hourly cleanup. SPEC 11 and 12 updated.

## 7. P12 precache reuse (`changes/p12-precache-reuse`)

Measure first with the existing `tools/perf` browser setup: bytes and time for a worker update where no asset changed versus one where one changed. Only if reuse saves a meaningful amount, build the precache list from content hashes and copy unchanged entries from the old cache during install, keeping the offline scanner and atomic install. If it doesn't pay, the branch holds only the measurement write-up.

## 8. P17 deploy probe (`changes/p17-deploy-probe`)

Tested locally against a stopped and restarted dev server. Not run against production until a deploy Antoan authorises; `deploy.sh` is not changed.

## 9. Recipes (`changes/recipes`)

The brainstorm's draft (docs/ideas/2026-10-11-brainstorm.md, 3.3), as Antoan chose:
- A recipe is a private `FoodItem` with `Source = Recipe`, never shared, no barcode; `Recipe` (`FoodItemId` key, `YieldGrams` nullable, `UpdatedAt`) and `RecipeIngredient` (`SortOrder`, `Description`, `Grams`, `FoodItemId` nullable, the per-100 g values used, snapshotted).
- `RecipeMath.Per100g` in Core with the draft's rules and tests: no yield uses the raw total, 20% to 300% yield limits, fiber and saturated fat known only when ingredients carrying them hold 95% of the kcal, 1 to 30 ingredients of 1 to 3,000 g.
- A Recipes group under Saved meals on the Recent tab, "New recipe" with a name, ingredients typed as text (parser and matcher onto a confirmation list, counted against the parse limit) or added from search, and "Weight when cooked (optional)". After saving, the recipe is an ordinary food in search, Recent, the grams sheet and parse matching; "Edit recipe" in its grams sheet. Entries keep their totals, so editing changes only later entries.
- Works without a key (search only). User isolation, export and `delete-user` covered. SPEC sections 4, 5.12, 7 and a Phase 18 entry; README.
